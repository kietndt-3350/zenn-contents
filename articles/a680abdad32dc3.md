## はじめに

2026年9月上旬、AnthropicとOpenAIがほぼ同時に新しいモデルを発表しました。**Claude Fable 5.1**と**GPT-6 Astra**です。

最初にざっと情報を見たときは、正直この2つはかなり似ているなと思いました。どちらもコンテキストウィンドウは100万トークン前後で、コーディングやreasoning、tool use、computer use、それに何ステップも続くタスクにも対応しています。API料金の基本部分も同じで、入力100万トークンあたり10ドル、出力100万トークンあたり50ドルです。

スペック表やベンチマークだけを見ていても違いは見えてきません。でも両社のドキュメントを読み込んでいくと、面白いポイントは「どっちのモデルが強いか」ではなく、両社がAIエージェントというものをどう捉えているか、その違いにあることに気づきました。

ここでは、AstraとFable 5.1の違いとして特に印象に残った5つのポイントを紹介します。

## 1. Claudeは「任せて自分でやらせる」、Astraは「動きながら操作できる」

2つのモデルを並べてみて、一番はっきり感じた違いがこれです。

Anthropicは、Fable 5.1のlong-running task（長時間続くタスク）を処理する能力をかなり強調しています。たとえば、こんなふうに一つずつ指示する代わりに、

```
ファイルAを読む
→ ファイルBを確認する
→ 関数Cを直す
→ テストDを実行する
```

もっと大きなゴールを渡せるようになりました。

```
このバグの原因を調べて直し、
テストを実行して結果を確認して
```

あとはどのファイルを読むか、どのコマンドを実行するか、テストが失敗したらどこを調べるか、モデルが自分で判断します。Anthropicの紹介の仕方を見ていると、「人がなるべく手を出さずに、AIが長い作業をやり切るにはどうすればいいか」という問いに強くフォーカスしている印象を受けます。

Astraも同じようなタスクをこなせますが、OpenAIはさらに、動いている最中のエージェントに割り込める仕組みを用意しています。一番わかりやすいのがMid-turn Steeringです。

例えば、リポジトリをチェックしてバックエンドとフロントエンドの両方を直してほしいとお願いしたとします。エージェントはリポジトリを読み、バックエンドを直し終えてフロントエンドの確認に入ったところで、要件が変わりますと

```
フロントエンドはもう直さなくていい、バックエンドだけでいい
```

Astraなら、タスクが走っている最中でもアプリケーション側から新しい指示をそのまま送れます。一度止めて最初からやり直す必要はありません。

一言でまとめるなら、

```
Claude → autonomy（自律性）
Astra  → 動いている最中に操作できること
```

を重視している、という感じです。これはあくまで設計上どこを強調しているかの違いで、Claudeが操作できないとか、Astraが自動で動けないという意味ではありません。

## 2. Astraは複数toolの並行処理をAPIレベルに近いところまで持ってきている

2つ目に面白いと思ったのが、Astraのasync tool callingです。

実際のエージェントは1つのtoolだけを使うことは少なく、複数のtoolを使うのが普通です。

```
GitHub
検索
データベース
ブラウザ
社内API
```

これを順番に処理すると、workflowは

```
toolAを呼ぶ → 待つ → 結果を受け取る → toolBを呼ぶ → 待つ → 結果を受け取る
```

という流れになります。問題は、toolによっては数秒、時には数十秒かかるものもあることです。

Astraでは、developerがtoolをasyncとして指定できます。そのtoolが動いている間、モデルは待ちぼうけを食らうのではなく、reasoningを続けたり、別の作業を並行して進めたりできます。

ここで大事なのは「Claudeはasyncができない」という話ではないということです。Claudeの上に構築するエージェントでも、アプリケーション層でconcurrencyを設計すること自体は十分可能です。違いは、OpenAIがこの仕組みをAstraのinteraction modelの中でかなり直接的に見せている、という点にあります。つまりdeveloperは「モデルがどのtoolを呼ぶか」だけでなく、「そのtoolが動いている間、モデルに何をさせるか」まで意識できるようになります。複数のAPIや外部サービスを使うエージェントにとっては、これはかなり実務的な違いです。

## 3. Claudeは相変わらず「coding agent」寄り、Astraはcomputer work全般に広がっている

どちらのモデルもコーディングはかなり強いので、最初はここを違いとして扱うつもりはありませんでした。ただ、両社の製品紹介の仕方を見ると、力を入れている方向はけっこう違います。

Claudeは今もrepository、terminal、git、test、IDE、code reviewといったworkflowと強く結びついています。特にClaude Codeでは、モデルがcodebaseと直接やり取りすることを前提にしたエコシステムをAnthropicが一つ作り上げています。彼らが想定するcoding taskはもう「この関数を書いて」ではなく、こんな一連の流れに近くなっています。

```
リポジトリを読む
→ 今の設計を理解する
→ 原因を探す
→ 複数ファイルを直す
→ テストを実行する
→ エラーを読む
→ また直す
→ verifyする
```

Fable 5.1もこの方向をさらに強めています。

Astraもコーディングをかなり前面に押し出していますが、対象範囲がもっと広いです。コード以外にも、こんな領域まで話が及びます。

```
ブラウザ
GUI
ドキュメント
スプレッドシート
業務ソフト
コンピュータ環境全般
```

ざっくり言うと、

```
Claude → Software Engineering Agent
Astra  → General Computer / Professional Work Agent
```

に近いイメージです。

もちろん重なる部分はかなり大きく、Claudeにもcomputer useはありますし、Astraのコーディング力も強いです。ただ、両社がモデルをどんな「製品」にしたいかという視点で見ると、これは無視できない違いだと思います。

## 4. Astraはreasoningを細かく調整できる、Claudeはモデル自身に任せる

Astraはreasoning effortをいくつかの段階でサポートしていて、application（利用者側）が作業の途中でもこのレベルを変えられます。

```
low
medium
high
xhigh
max
```

例えば、READMEを読むだけならlow、簡単なCRUDを直すならmedium、難しいバグを調査するときはhigh、architectureを分析するときはxhigh、というふうに使い分けられます。この考え方はdeveloperにとってわかりやすいものです。すべてのステップで同じだけreasoningが必要なわけではなく、reasoningを上げるほどlatencyもcostも増えていくからです。

一方Fable 5.1はAdaptive Thinkingという仕組みを採用しています。Anthropicの考え方は、application側が各フェーズを細かく管理するのではなく、タスクに応じてモデル自身が必要なreasoning量を調整する、というものです。

簡単に言うと、

```
Astra  → 「このタスクは難しいから、もっと考えて」と伝える
Claude → タスクを渡すだけで、考える量はモデルに任せる
```

というスタイルの違いです。どちらが正解ということはなく、costやlatencyを厳密にコントロールしたいシステムならAstraの調整力が魅力的ですし、application側のorchestrationを減らしてモデルに判断を委ねたいならClaudeのやり方の方が自然だと思います。

## 5. API価格は同じでも、long-running agentのコストは同じとは限らない

料金表を見ていて危うく見落としそうになったのがprompt cachingです。

2つのモデルの基本料金はまったく同じです。

```
10＄・入力100万トークンあたり
50＄・出力100万トークンあたり
```

ここまでだとcostは差別化要因にならなさそうです。でもcached inputの料金はけっこう差があります。

```
Astra     : 1＄・cached inputトークン100万あたり
Fable 5.1 : 0.25＄・cache readトークン100万あたり
```

普通のchatbotであれば、この差はそれほど大きくありません。でも長時間動くagentの場合、system prompt、project instructions、repositoryのcontext、tool定義、会話履歴が何十ステップにもわたって使い回されるので、cache readの部分が総コストの中でかなりの割合を占めます。つまり、入力・出力の単価が同じだからといって、実際のタスク1つあたりのコストが同じになるとは限らないということです。

これを見ていて、AI Agentにとって意味のある指標はもうprice per token（トークン単価）ではなく、cost per successful task（タスク成功あたりのコスト）なのかもしれない、と思うようになりました。1回のrequestあたりは高くても、retryが少なかったり、人の介入が少なかったり、contextの再利用効率が良かったりすれば、トータルのコストはむしろ低くなることもあるはずです。

## ベンチマークは何を示しているのか

AIの文脈でのbenchmark（ベンチマーク）とは、モデルの能力を測って比較するための標準化されたテストのことです。

作業を自動でやり切る能力を測るいくつかのベンチマークでは、AstraがClaudeより高いスコアを出しています。

ただし、ベンチマークのスコアが高い = 実際の性能が良い、とは限りません。ベンチマークの点数が高いモデルが、必ずしもあなたのプロジェクトに向いているとは限らないのです。

そういうこともあり、ベンチマークについてはこの記事であまり深掘りするつもりはありません。現行のfrontier modelは直接比較するのがかなり難しいからです。automation寄りのevaluationではAstraがFable 5.1より高いスコアを出す一方、総合的なintelligenceを測る別のベンチマークではFable 5.1の方が上、というケースもあります。

これは十分理にかなっています。両モデルとも十分強くなった結果、「どっちが勝ちか」という問いにもう一つの正解では答えられなくなっているからです。エージェントの実際のパフォーマンスは、モデルだけでなく、こういった要素にも左右されます。

```
prompt
tool
agent harness
context
environment
retry strategy
```

## まとめ・では、どのモデルを選ぶべきか

私自身、こういった作業には今までずっとSonnet 5モデルをメインで使ってきました。速くて安く、コードを読む・バグを直す・リファクタリングする・テストを実行してPRを出す、といったタスクであればそれで十分だからです。わざわざ重量級のモデルを持ち出す必要はありません。Fable 5.1と並べてみると、一番違いを感じるのはmulti-stepなタスクにおける自律性のレベルです。Sonnet 5だと自分がそばについて作業を細かく分割してあげる必要がまだ結構ありますが、Fable 5.1はこんな一連の流れを人の介入少なめで一気に回せるように作られています。

```
読む
→ 直す
→ テストする
→ verifyする
```

つまりSonnet 5が劣っているというより、2つのモデルが狙っている「作業の任せ方」のレベルがそもそも違う、ということだと思います。

Astraと比べた場合はどうかというと、プログラマーの日々の仕事に関して言えば、Fable 5.1の方が理にかなった選択だと今のところ思っています。この手の作業はだいたい同じパターンの繰り返しなので、ゴールを丸ごと渡してモデルにそのループを回させる方が、一歩ずつ付きっきりで指示するより実際の時間の節約になります。同じリポジトリで1日に何度もタスクを連続実行するなら、Fable 5.1の安いprompt cacheの差も積み重なって効いてきます。

Astraの仕組み――途中で操作できたり、複数toolを並行処理できたりする点――が本当に活きるのは、複数のservice/toolを組み合わせて動かすagentを作るような仕事だと思います。普段のコーディング作業ではそこまで恩恵は大きくありません。なので、日々のプログラミング作業だけを考えるなら、私は今のところFable 5.1寄りです。

5つの違いのまとめ:

|                    | GPT-6 Astra                  | Claude Fable 5.1                                        |
| ------------------ | ---------------------------- | ------------------------------------------------------- |
| 働き方             | Interactive / controllable   | Autonomous / long-running                               |
| Tool orchestration | asyncをわりと直接的に公開    | agent/applicationのアーキテクチャ側で処理することが多い |
| 得意な使われ方     | Computer / professional work | Coding / software engineering                           |
| Reasoning          | developerが細かく調整できる  | Adaptive Thinking                                       |
| Prompt cache       | 高め                         | かなり安い                                              |
