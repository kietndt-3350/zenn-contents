# はじめに

Amazon、楽天市場、Temu などのECサイトを利用していると、次のようなレコメンドをよく見かけます。

- Frequently Bought Together
- Customers Also Bought
- Recommended for You
- Similar Products

ユーザーから見ると、単に「システムがいくつかの商品を選んで表示している」ように見えます。

しかし、その裏側では、購入履歴、商品情報、検索履歴、クリック、カート、ユーザーごとの好みなど、さまざまなデータが使われています。

最近、私はECサイトの商品レコメンドシステムの調査・改善に関わる機会がありました。その中で、レコメンドシステムは必ずしも最初からAIや複雑な機械学習モデルを使う必要はない、ということに気づきました。

出発点は、次のような非常にシンプルな問いでも十分です。

> **「商品Aを購入したユーザーは、商品Bも購入する可能性があるのか？」**

そこから、より精度の高いレコメンドを目指すために、少しずつ **Product** を理解し、最終的には **User** を理解していく必要があります。

この記事では、この3つのステップを通して、レコメンドシステムがどのように作られていくのかをざっくり見ていきます。

---

# 1. Co-purchase — 一緒に購入される商品から学ぶ

## 1.1. `P(B | A)` の確率

例えば、次のようなデータがあるとします。

```text
商品Aを含む注文数: N(A) = 500
商品AとBの両方を含む注文数: N(A ∩ B) = 80
```

このとき、条件付き確率 `P(B | A)` は次のように計算できます。

```text
P(B | A) = N(A ∩ B) / N(A)
         = 80 / 500
         = 16%
```

つまり、

> 商品Aを含む注文のうち、16%では商品Bも一緒に購入されている

という意味です。

---

## 1.2. `P(B | A)` と `P(A | B)` は同じではない

それぞれ、

```text
P(B | A) = N(A ∩ B) / N(A)

P(A | B) = N(A ∩ B) / N(B)
```

となります。

分子の `N(A ∩ B)` は同じですが、分母が `N(A)` と `N(B)` で異なるため、

```text
P(B | A) ≠ P(A | B)
```

となる場合があります。

例えば、

```text
Camera → SD Card
```

カメラを買った人はSDカードも必要になる可能性が高いですが、SDカードを買った人が必ずカメラも必要になるわけではありません。

---

## 1.3. `Lift(A → B)`

`P(B | A)` が高くても、商品B自体がもともと人気の商品である可能性があります。

そこで使えるのが **Lift** です。

```text
Lift(A → B) = P(B | A) / P(B)
```

ここで、

```text
全注文数: N
商品Bを含む注文数: P(B) = N(B) / N
```

です。

例えば、

```text
P(B | A) = 16%
P(B)     = 2%

Lift(A → B) = P(B | A) / P(B)
            = 16% / 2%
            = 8
```

となります。

つまり、Aを買った人は、通常と比べて約8倍Bを買いやすいと考えることができます。

---

# 2. 商品の特徴をベクトル化する

商品には、例えば次のようなさまざまな特徴があります。

```text
Title
Description
Category
Brand
Price
Color
Attributes
Image
```

こうした特徴を数値に変換し、1つのベクトルとして表現することができます。

```text
Product A = [a1, a2, a3, ..., an]
Product B = [b1, b2, b3, ..., bn]
```

このような商品のベクトル表現は、一般的に **Product Embedding** と呼ばれます。

重要なのは、

> **特徴や意味が似ている商品ほど、ベクトル空間上でも近い関係になる**

という考え方です。

では、2つのProduct Vectorがどのくらい似ているかを、どうやって判断するのでしょうか。

その方法の1つが **Cosine Similarity（コサイン類似度）** です。

2つの商品ベクトルを `A`、`B` とすると、Cosine Similarityは次のように計算できます。

```text
cosine_similarity(A, B) = (A · B) / (||A|| × ||B||)
```

これは簡単に言うと、**2つのベクトルが作る角度の近さ**を見る方法です。

```text
角度が小さい
    ↓
ベクトルの向きが近い
    ↓
類似度が高い
```

例えば、

```text
cosine_similarity ≈ 1
→ 非常に似ている

cosine_similarity ≈ 0
→ あまり似ていない
```

と考えることができます。

この方法を使うことで、過去に一度も一緒に購入されていない商品同士でも、商品自体の特徴から似ている商品を見つけ、レコメンド候補として利用できます。

つまり、Product Vectorを使うことで、

> **「Aと特徴や意味が似ている商品は何か？」**

という視点でもレコメンドできるようになります。

ただし、商品同士が似ているだけでは、その商品がすべてのUserに合うとは限りません。

そこで次は、Productだけではなく、**Userの行動や好み**についても考えていきます。

---

# 3. ProductだけでなくUserも理解する

同じ商品を見ているUserでも、興味や目的はそれぞれ違います。

そこでPersonalized Recommendationでは、

> **「このUserに最も合う商品は何か？」**

という視点で考えます。

Userについても、例えば次のようなさまざまなデータを利用できます。

```text
Purchase History

Click History

Search History

Wishlist

Cart

Recently Viewed

Preferred Categories

Preferred Brands
```

こうしたデータから、Userの興味や好みをベクトルとして表現することができます。

```text
User Vector
     ↓
Product Vectorsと比較
     ↓
Userに近いProductをレコメンド
```

Product Vectorと同じように、User VectorとProduct Vectorの近さを見ることで、そのUserに合いそうな商品を探すことができます。

ただし、Userの興味はいつも同じとは限りません。

長期的にはTechnology系の商品をよく見ているUserでも、最近は全く別のカテゴリの商品を探しているかもしれません。

そのため、実際のレコメンドでは、

```text
Long-term Preference
        +
Short-term Intent
        +
Current Context
```

のように、複数の情報を組み合わせて考えることができます。

Current Contextには、例えば次のような情報があります。

```text
時間

季節

直近の検索

直近で見た商品

直近で購入した商品
```

つまり、ここまで来るとレコメンドは単純な、

```text
Product A → Product B
```

という関係だけではなく、

```text
User
 +
Product
 +
Behavior
 +
Context
     ↓
Recommended Products
```

として考えられるようになります。

このように、ProductだけではなくUserの行動や今の状況も合わせて見ることで、よりPersonalizedなレコメンドができるようになります。

---

# まとめ

シンプルに整理すると、レコメンドシステムは次の3つのステップで考えることができます。

```text
Co-purchase
    ↓
Productを理解する
    ↓
Userを理解する
```

最初は「どの商品が一緒に購入されているか」を見るだけでも始められます。そこから商品の特徴を追加し、さらにユーザーの行動や好みを取り入れることで、よりパーソナライズされたレコメンドが可能になります。

Amazon、楽天、Temuなどの実際の商品レコメンドシステムはもちろんこれよりはるかに複雑ですが、この3つの考え方は、レコメンドシステム全体を大まかに理解するための1つのシンプルな見方だと思います。
